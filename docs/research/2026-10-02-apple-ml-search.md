# Спайк: поиск по содержимому на родных ML-данных iPhone

Дата: 2026-10-02. Ветка: `hp/omaimediateka/t-0002-ml-iphone`.
Метод: только чтение копий баз по AFC (gvfs), оригиналы на телефоне не изменялись.

## Короткий вывод

**Да.** На iPhone уже лежит готовый поисковый индекс Apple Photos, и его можно
переиспользовать. Поиск по смыслу («рыбалка», «рыба», «fish», «документ»)
работает: запрос «рыб» дал 47 осмысленных ассетов из родных данных, «fish» —
ещё 16 через англоязычные caption'ы. Свои модели обучать не нужно.

Данные лежат в `PhotoData/Photos.sqlite` (индекс «Leo»: сцены, OCR-текст,
классы документов, люди, места) и `MediaAnalysis/MediaAnalysis.sqlite`
(сцены/labels + естественно-языковые caption'ы кадров и видео). Связь с файлами
DCIM — через `ZASSET.ZUUID`.

Проверка на честность: несколько найденных файлов открыты глазами по превью —
сцены совпали (рыбалка и рыба). Теги не врут.

## Что и где лежит

### Photos.sqlite (215 МБ на телефоне)

| Таблица | Что это | Строк |
|---|---|---|
| `ZASSET` | ассеты: `ZUUID`, `ZFILENAME`, `ZDIRECTORY`, `ZDATECREATED` | 3522 |
| `ZLEOLEXEME` | словарь поисковых «лексем»: `ZLEXEMEID`, `ZCATEGORY`, `ZCONTENT` (текст), `ZIDENTIFIER` | 23679 (18738 уникальных id) |
| `ZLEOITEM` | ассет → список лексем: `ZIDENTIFIER` (= UUID ассета), `ZLEXEMEIDSDATA` (BLOB) | 3504 (itemtype=1) |
| `ZSCENECLASSIFICATION` | покадровые сцены (scene id + confidence) | 176248 |
| `ZCHARACTERRECOGNITIONATTRIBUTES` | OCR: `ZCHARACTERRECOGNITIONDATA` (проприетарный архив) | 3522 |
| `Z_LeoLexeme_byContentFTSv2` | FTS5-индекс по `ZCONTENT` (кастомный tokenizer) | — |

`ZLEOITEM.ZLEXEMEIDSDATA` — это массив little-endian `uint32`: первое слово =
версия формата (сейчас `2`), дальше — значения `ZLEOLEXEME.ZLEXEMEID`. Поэтому
чистого SQL мало, нужен разбор BLOB (5 строк на Python).

Категории `ZLEOLEXEME.ZCATEGORY` (проверено на этой библиотеке):

| Категория | Смысл | Ассетов с ней |
|---|---|---|
| `4000` | сцены/объекты (`scene/305` → «Картонная коробка») | 3359 |
| `4090` | активности/события (`meaning/10` → «Концерт») | 462 |
| `4120` | **OCR-токены** («рыбалка», «рыболовства», «fishtec») | 1478 |
| `4130` | классы документов («Водительские права») | 181 |
| `4110` | маркер «Найденный текст» (у ассета есть OCR) | 1479 |
| `3000` | люди (имена, привязка по UUID человека) | 1436 |
| `2030`/`2050` | места/POI, названия улиц | 928 / 1616 |
| `1040`/`1050`/`1060` | сезон / время суток / будни-выходные | ~3504 |

Локализация родная: тексты сцен и OCR на русском (язык телефона). Английские
запросы в этих лексемах не находятся (кроме реально распознанного латинского
текста вроде `fish`).

### MediaAnalysis.sqlite (114 МБ)

| Таблица | Что это | Строк |
|---|---|---|
| `ZASSET` | ассеты Vision: `ZLOCALIDENTIFIER` = `<UUID>/L0/001` | 3507 |
| `ZIMAGECAPTIONRESULT` | **описание кадра**: `ZCAPTION` (англ.), `ZCONFIDENCE` | 3498 |
| `ZVIDEOCAPTIONRESULT` | **описание видео** | 1175 |
| `ZSCENERESULT` / `ZCLASSIFICATIONRESULT` | эмбеддинги сцены / scene id + confidence | 935 / 25036 |
| `ZSENTENCELEVELTRANSCRIPTIONRESULT` | транскрипция речи | 0 (пусто) |

Примеры caption'ов: `a child sitting on a boat holding a fish`,
`a close up of fish fillets on a sheet of aluminum foil`. Средняя уверенность
0.50 (фото) и 0.56 (видео). Язык — только английский.

Связь: `MediaAnalysis.ZASSET.ZLOCALIDENTIFIER[:36]` = `Photos.ZASSET.ZUUID`.

### `MediaAnalysis/vector_database/index.sql` (18 МБ)

Отдельная SQLite-база GRDB-векторного индекса:

- `observations`: 10870 векторов по **512 измерений, float16** (1024 байта),
  L2-норма ≈ 1.0 — пригодны для косинусной близости;
- `attributes`: `asset_id` вида `<UUID>/L0/001_1`, `vector_id`,
  `embeddingVersion=10`; префикс `asset_id` совпадает с `ZASSET.ZUUID`;
- `partitions`: 103 центроида (та же размерность);
- `documents`, `metadata` (dimension=512), FTS по метаданным.

Это эмбеддинги Apple для **поиска по образцу** (фото → похожие). Для поиска по
тексту их переиспользовать нельзя: текстового энкодера, согласованного с этим
пространством, в системе нет. Оценка: читать их реально (формат простой), но
это отдельная задача «найти похожие на это фото», а не «найти по слову».

## Запрос (проверенный)

Логика, которая дала результат (полная версия — `library/iphone-ml-search.py`):

1. `SELECT ZLEXEMEID, ZCATEGORY, ZCONTENT FROM ZLEOLEXEME` — отобрать
   `ZLEXEMEID`, где `lower(ZCONTENT) LIKE '%<терм>%'`.
2. Для каждого `ZLEOITEM` (itemtype=1): `struct.unpack('<%dI', blob)`, взять
   элементы начиная со второго, пересечь с найденными id.
3. `ZLEOITEM.ZIDENTIFIER` = `ZASSET.ZUUID` → `ZDIRECTORY || '/' || ZFILENAME`.
4. Дополнительно в `MediaAnalysis.sqlite`:
   `ZIMAGECAPTIONRESULT`/`ZVIDEOCAPTIONRESULT` JOIN `ZASSET` по `Z_PK`,
   фильтр `lower(ZCAPTION) LIKE '%fish%'`, `ZLOCALIDENTIFIER[:36]` → UUID.

Пример SQL-скелета (без разбора BLOB, только словарь):

```sql
-- какие лексемы вообще есть по теме
SELECT ZLEXEMEID, ZCATEGORY, ZCONTENT
FROM ZLEOLEXEME
WHERE lower(ZCONTENT) LIKE '%рыб%';

-- связка ассет ↔ лексемы (BLOB парсится в приложении)
SELECT i.ZIDENTIFIER, i.ZLEXEMEIDSDATA, a.ZDIRECTORY, a.ZFILENAME
FROM ZLEOITEM i JOIN ZASSET a ON a.ZUUID = i.ZIDENTIFIER
WHERE i.ZITEMTYPE = 1;
```

Тайминги после копирования баз: поиск **0.1 с**, копирование ~350 МБ по AFC —
**~7 с** (Photos.sqlite 215 МБ + MediaAnalysis 114 МБ + vector_database 18 МБ).

## Почему не читаем «сырой» OCR

`ZCHARACTERRECOGNITIONATTRIBUTES.ZCHARACTERRECOGNITIONDATA` — это
`NSKeyedArchiver` (bplist), внутри поле `kCROutputRegionData` с бинарным
сжатым форматом Apple Vision. Полного текста как строки там нет; наружу
отдаются только токены в `ZLEOLEXEME` (категория 4120). Для поиска токенов
достаточно, но показать «весь распознанный текст» из родных данных не выйдет.

## Дополнение 2026-10-04: остальные метки MediaAnalysis (реализовано, t-0005)

После внедрения поиска выяснилось, что `MediaAnalysis.sqlite` — это не только
caption'ы. Полезное и не дублирующее уже проиндексированное:

| Таблица | Что даёт | Строк (эта библиотека) |
|---|---|---|
| `ZVIDEOSEGMENTCAPTIONRESULT` | caption'ы по сегментам видео (англ.): заметно подробнее общего caption'а ассета | 9556 / 439 ассетов |
| `ZCLASSIFICATIONRESULT` | `ZSCENEID` + `ZCONFIDENCE` по кадрам; id переводятся в русские метки через `Photos.ZLEOLEXEME` (`scene/NNN`) | 25036 / 97 видео |
| `ZHUMANACTIONCLASSIFICATIONRESULT` | `nsaction`-блоб `{"<id>": conf}`; id → `humanAction/NNN` («Прогулка», «Танец», «Бег») | 729 / до 45 ассетов |
| `ZPETSRESULT` | факт питомца в кадре (без вида) — одна общая метка | 73 / 10 ассетов |

Что решили **не** брать: `ZSCENERESULT`/`ZRESULT` (эмбеддинги),
`ZSAFETYRESULT.ZSENSITIVITY` (чувствительный контент, приватность),
`ZANIMALRESULT` (15 строк, вид не идентифицируется — таксономия животного
недоступна), `ZVOICERESULT`/`ZMUSICRESULT` (дублируют аудио-лексемы Leo),
`ZHUMANPOSERESULT` (только скелет без метки).

Порог уверенности обязателен: без него на видеокадрах в индекс попадает шум
(«Егра», «Континентальные шельфы» при 0.56). Взяли 0.3 для сцен и действий и
0.7 для питомцев. Сцены кардинально не дублируют Leo: у этих 97 видео уже
есть какие-то сцены из Leo, а анализ по кадрам добавляет ещё метки
(например «Снег», «Зима»).

Замеры на этой библиотеке (сравнение старого и нового кэша по числу ассетов
в выдаче): «прогулка» 6 → 38, «питомец» 0 → 10, «sunglasses» 46 → 69,
«fishing rod» 9 → 22, «life jacket» 4 → 10.

### Оценка шума и порог 0.5

- **Питомцы (0.7)** — точность высокая: глазами подтверждены собака и кошка;
  но есть пограничный случай — видео с мангалом с conf 0.71–0.73 попало в
  выдачу (вероятно, питомец есть в другом кадре, либо ложное срабатывание).
- **Сцены (0.3)** — глазами «Снег»/«Зима»/«Замороженное» на зимнем видео
  подтверждены. Порог **0.5** не убирает ни одного из 97 видео, но режет
  число меток-пар с 13 233 до 9 028 (−32 %): исчезают самые шумные
  низкоуверенные сцены.
- **Действия (0.3)** — шумно: «Пешком» (id 2) ловится на прогулках, но
  иногда и на видео со спортзалом, где более точное «Игра в футбол» (id 25)
  имеет лишь 0.10 и не проходит. Порог **0.5** оставляет 30 ассетов вместо
  45 (−15) и 145 меток-пар вместо 224.
- Отдельно от порогов шумит сам caption: например, ролик с ребёнком в
  VR-шлеме Apple описала как «shirtless child … and sunglasses», поэтому
  «sunglasses» его находит. Это свойство исходных данных, а не нашей логики.

Решение пользователя: пока оставить сцену на 0.3; 0.5 — готовый кандидат на
ужесточение, если ложные сцены будут мешать.

## Риски

- **Проприетарно и недокументировано.** Схема `ZLEO*` и формат BLOB не
  гарантированы; обновление iOS может сменить таблицы, категории или версию
  BLOB. Нужен graceful degradation и проверка версии при разборе.
- **Только чтение копий, не живых баз.** Копировать основные файлы и `-wal`/`-shm`
  и схлопывать WAL; иначе можно получить несогласованный снимок.
- **Объём копирования** ~350 МБ на каждое обновление; кэшировать и обновлять по
  факту подключения кабеля, а не на каждый поиск.
- **Язык.** Лексемы сцен/OCR локализованы (русский); caption'ы — английские.
  Смешанный запрос даст разные наборы.
- **Персональные данные.** Категория 3000 содержит имена людей; всё локально,
  никуда не отправляем и не логируем имена.
- **Не всё покрыто.** ~0.5 % ассетов без ML, 12 облачных ассетов, Live Photo
  MOV-компоненты отдельно не индексируются (парный HEIC индексирован).

## Резерв, если гипотеза бы не подтвердилась

- **Свой OCR:** `tesseract` с `rus`+`eng` уже стоит. Разовая прогонка 4305
  файлов (HEIC сначала через `heif-convert`), затем FTS по тексту. Дольше
  (десятки минут) и качество ниже Apple, зато не зависит от схемы.
- **CLIP на GTX 1660:** закодировать ~4300 изображений (ViT-B/32…L/14, fp16,
  6 ГБ хватает), затем искать текстом. Даёт открытый словарь и «смысл», но
  требует скачать модель и выбрать мультиязычный вариант (или переводить
  запрос), и это отдельный пайплайн.
