# Omaimediateka — плагин медиатеки iPhone для Omarchy Shell

- Дата: 2026-10-01
- Статус: этап 1 (черновик к реализации)
- Репозиторий: `omaimediateka`

## 1. Цель

Плагин Omarchy Shell (Quickshell) показывает фото и видео с iPhone,
подключённого **USB-кабелем**. Виджет живёт в центре бара; по клику
открывается попап по центру экрана с сеткой превью из `DCIM` и
полноэкранным просмотром выбранного элемента.

Ориентир по устройству — существующий плагин
`~/.config/omarchy/plugins/omarchy-ssh-connections` (`kinds: bar-widget`,
`entryPoints.barWidget`, кнопка-пилюля в баре + `KeyboardPanel`).

## 2. Границы этапа 1 (не расширять)

Входит:

- Сетка превью фото/видео из `DCIM` подключённого iPhone.
- Полноэкранный просмотр выбранного элемента (изображение; видео — кадр
  и воспроизведение, если доступно).
- Определение состояния: телефон подключён / не подключён / не доверен /
  нет системного бэкенда.
- Кэш превью в `~/.cache/omaimediateka/`, ленивая генерация.

Не входит:

- Импорт/копирование на компьютер, удаление с телефона.
- Музыка, книги, прочие файлы, доступ к приложениям.
- Поиск по метаданным (EXIF/GPS/лица), альбомы «Фото», живые фото как видео.
- Wi-Fi / облако / AirDrop — только USB.

## 3. Доступ к DCIM: выбор бэкенда

Есть два практических способа увидеть `DCIM` iPhone как файлы.

### Вариант A — gvfs-afc (GIO virtual filesystem)

- Пакет `gvfs-afc` (официальный `extra`), зависимости: `libimobiledevice`,
  `libusbmuxd`.
- Открывает `afc://<UDID>/` и отдаёт его через `gvfsd-fuse` в
  `$XDG_RUNTIME_DIR/gvfs/afc:host=<UDID>/`.
- Монтирование делает сессия gvfs: том `afc` подхватывается
  `gvfs-afc-volume-monitor` (D-Bus-активируемый), либо вручную
  `gio mount afc://<UDID>/`. `gvfsd-fuse` в системе уже запущен.
- Состояние проверяется по `idevice_id -l` (usbmuxd), доверие — по
  `idevicepair -u <UDID> validate`.

Плюсы:

- Официальный пакет, ставится без AUR.
- Монтаж/размонтирование автоматические: выдернул кабель — путь исчез.
- Никакого root: монтирует пользовательская сессия.
- Интеграция с рабочим столом (Nautilus, диалоги выбора файла).

Минусы:

- Чтение идёт через FUSE → накладные расходы на `stat/open` каждого файла;
  на тысячах файлов листинг и превью медленнее прямого монтирования.
- `mtime`/`size` из AFC через gvfs иногда врут (0 или дата монтирования),
  поэтому нельзя слепо полагаться на дату из `stat`.
- Ошибки gvfs не всегда различимы (нет кода ошибки на стороне QML).

### Вариант B — ifuse (FUSE из libimobiledevice)

- Пакет `ifuse` (официальный `extra`).
- Пользователь запускает `ifuse <точка монтирования>`, том живёт до
  размонтирования/отключения.
- Требует `/dev/fuse` и прав пользователя на fuse (в Arch это есть по
  умолчанию), root не нужен.

Плюсы:

- Обычная файловая система: честные `stat`, `mtime`, `size`, `readdir`.
- Детерминированная точка монтирования, полный контроль жизненного цикла.
- Прямые `open/read` без двойного слоя FUSE поверх gvfs.

Минусы:

- Нет авто-монтирования: плагин обязан сам поднимать `ifuse`, следить за
  процессом и размонтировать при отключении.
- При выдёргивании кабеля точка монтирования «зависает»; любые `stat`
  виснут → нужен таймаут на каждую файловую операцию.
- Стало быть, плагин (Quickshell) становится родителем долгоживущего
  процесса — при перезапуске шелла остаются stale-монтирования.

### Решение

**Бэкенд этапа 1 — вариант A, `gvfs-afc`.**

Причины: официальный пакет, нулевой root, автоматический монтаж и
автоматический распад при отключении (нечему «зависать»), `gvfsd-fuse`
в системе уже поднят. Производительность на этапе «только просмотр» с
ленивым кэшем превью приемлема, а ненадёжный `mtime` компенсируется
сортировкой по именам файлов Apple (см. §6).

`ifuse` описан как запасной путь и **не реализуется** в этапе 1. Вся
работа с файлами изолирована в скрипте-хелпере, поэтому добавление
ifuse-бэкенда позже не потребует правок QML.

Альтернатива, рассмотренная и отклонённая: `usbmuxd`/`afcclient` вручную
(в libimobiledevice есть `afcclient`, но он не отдаёт файловую систему и
требует собственной обвязки на каждый `read`). Для интерфейса «сетка
превью» неудобен.

## 4. Что требуется от пользователя (только инструкция, поток не делает)

```bash
# 1. Бэкенд доступа к DCIM
sudo pacman -S gvfs-afc

# 2. usbmuxd. Служба статическая и НЕ включается через enable:
#    её поднимает udev при подключении iPhone (правило 39-usbmuxd.rules).
#    Можно стартовать и вручную:
sudo systemctl start usbmuxd

# 3. Подключить iPhone кабелем, разблокировать, на телефоне нажать «Доверять».
```

Проверка, что всё готово:

```bash
idevice_id -l                       # UDID -> строка(и)
idevicepair -u <UDID> validate      # SUCCESS: Validated pairing
ls "$XDG_RUNTIME_DIR"/gvfs/afc:host=*   # появился DCIM/
```

Поток (агент) **не запускает sudo и не трогает систему** — выше
приведена инструкция для пользователя.

Без установленного бэкенда плагин показывает понятное состояние
«Нет доступа к iPhone» с этими командами, но не пытается их выполнить.

## 5. Жизненный цикл устройства и состояния

Источник правды — `bin/oma-mediateka status`, печатает одну JSON-строку:

```json
{
  "state": "ready",
  "backend": "gvfs",
  "udid": "<UDID>",
  "mount": "$XDG_RUNTIME_DIR/gvfs/afc:host=<UDID>",
  "dcim": "$XDG_RUNTIME_DIR/gvfs/afc:host=<UDID>/DCIM",
  "message": ""
}
```

Состояния:

| state        | Когда                                        | Что показывает попап                    |
|--------------|----------------------------------------------|-----------------------------------------|
| `no-tools`   | нет `idevice_id` (libimobiledevice)          | инструкция по установке                 |
| `no-device`  | usbmuxd жив, но UDID не найден               | «iPhone не подключён» + шаги            |
| `unpaired`   | устройство есть, `idevicepair validate` ≠ 0  | «Нажмите Доверять на iPhone»            |
| `no-backend` | спарен, но `gvfs-afc` отсутствует и монтирования нет | «Установите gvfs-afc» с командой |
| `mounting`   | бэкенд есть, монтирование ещё идёт           | спиннер                                 |
| `no-dcim`    | монтирование есть, `DCIM` нет                | «Разблокируйте iPhone» / «Нет DCIM»     |
| `ready`      | `DCIM` доступен                              | сетка                                   |
| `error`      | непредвиденное                               | текст ошибки                            |

Логика `status`:

1. `command -v idevice_id` — иначе `no-tools`.
2. `idevice_id -l` — иначе `no-device`.
3. `idevicepair -u <UDID> validate` — иначе `unpaired`.
4. Ищем каталог `$XDG_RUNTIME_DIR/gvfs/afc:host=<UDID>*`.
   Если нет и установлен `gvfs-afc` (`/usr/lib/gvfsd-afc`),
   один раз пробуем `timeout 15 gio mount afc://<UDID>/` и ищем снова
   (`mounting`, если попытка в процессе/не удалась сразу).
5. Если `DCIM` существует → `ready`, иначе `no-dcim`.

Детекция в QML: таймер опроса (4 с в закрытом попапе, 2 с в открытом).
Дополнительно `status` вызывается при открытии попапа. Смена `state` или
`mount` → пересборка списка. Опрос при закрытом попапе лёгкий (shell
без `find`), поэтому фоновая проверка не грузит систему.

Отключение: путь gvfs исчезает сам, `status` переходит в `no-device`,
список и превью сбрасываются.

## 6. Обход DCIM

`bin/oma-mediateka list <dcim>` — один проход `find`:

```bash
find -L "$dcim" -type f \
  \( -iname '*.jpg' -o -iname '*.jpeg' -o -iname '*.png' -o -iname '*.heic' \
     -o -iname '*.heif' -o -iname '*.webp' -o -iname '*.gif' \
     -o -iname '*.mp4' -o -iname '*.mov' -o -iname '*.m4v' \) \
  -printf '%T@\t%s\t%p\n'
```

- `find` строит вывод одним проходом, без `stat` на каждый файл.
- Отбрасываются sidecar-файлы Apple (`.AAE`, `.THM`), скрытые файлы и
  `__MACOSX`.
- Строка TSV: `mtime \t size \t path`; базовое имя, расширение и тип
  (photo/video) вычисляются в JS-модели.
- Папки вида `100APPLE`, `101APPLE`, … прозрачно обходятся `find`;
  отдельной логики для дерева не нужно.

Сортировка (в `MediaModel.js`, покрыта тестами):

1. Основной ключ — «номер» в имени файла (`IMG_1234` → 1234), затем номер
   папки (`100APPLE` → 100). Это хронология Apple и она не зависит от
   вранья gvfs `mtime`.
2. Дополнительный ключ — `mtime`, затем путь.
3. По умолчанию порядок **от новых к старым**; есть переключатель
   «старые → новые» в шапке.

Имена без числового суффикса (например, `IMG_E1234`) получают тот же
номер, что и оригинал, и сортируются по имени рядом.

## 7. Превью: HEIC/HEVC, кэш, ленивая генерация

Проблема: ffmpeg в системе собран **без** демуксера HEIF (проверено:
`ffmpeg -formats` не содержит heif/heic), а Qt6-плагин imageformats
тоже не декодирует HEIC. Поэтому HEIC декодирует `heif-convert`
(libheif), а HEVC-видео — ffmpeg (HEVC-декодер есть).

Инструменты:

- Фото JPEG/PNG/WebP/GIF → `ffmpeg` (`-frames:v 1 -vf scale=…`).
- Фото HEIC/HEIF → `heif-convert -q 80` во временный JPEG, затем
  `ffmpeg` для масштаба.
- Видео MOV/MP4/M4V → `ffmpeg -ss 0.5 -i … -frames:v 1 -vf scale=…`.
- Длительность видео — `ffprobe` (лениво, при открытии в просмотрщике).

Кэш:

- `~/.cache/omaimediateka/thumbs/<hash>.jpg` — сетка, до 384 px.
- `~/.cache/omaimediateka/previews/<hash>.jpg` — просмотр, до 2048 px.
- `<hash>` = djb2 от `path|mtime|size|вариант`, считается в JS и
  передаётся хелперу; сам скрипт ничего не хэширует.
- Скрипт идемпотентен: если JPEG на месте и непустой — выходит сразу.

Ленивая генерация:

- Делегат сетки при создании (GridView создаёт только диапазон
  `cacheBuffer`) ставит элемент в очередь запросов.
- Очередь в QML качает **один** `Process` за раз (без параллельных
  ffmpeg), по завершении — следующий. Дубликаты отсекаются по `key`.
- После успеха `thumbState[key] = true` (переприсваивается объект целиком,
  чтобы сработали биндинги), `Image` переключает `source` с `""` на файл.
- Просмотрщик отдельно запрашивает preview-вариант.

Так на экране одновременно не больше нескольких десятков декодирований,
и тысячный альбом открывается мгновенно, показывая то, что видно.

## 8. Производительность при тысячах файлов

- Листинг — один `find`; при 10 000 файлов это сотни КБ TSV, парсится в JS
  за миллисекунды.
- Сетка — `GridView` с `cacheBuffer`, без создания Item на каждый файл.
- Превью — только для видимых/соседних ячеек, один фоновый декодер.
- Никаких предварительных `stat` в QML: всё, что нужно, вычисляется из TSV.
- При смене состояния/отключении незавершённая генерация просто
  отбрасывается (проверкой `currentThumbKey`), новые запросы не ставятся.

## 9. UI/UX

Бар (пилюля, как в ssh-плагине):

- Иконка камеры + подпись «iPhone» + чип со числом элементов.
- Нет телефона → пилюля приглушена, чип пуст/точка.
- Идёт скан → лёгкая индикация.

Попап (`KeyboardPanel`, `centerOnBar: true`):

- `PanelHero`: «Медиатека iPhone», мета — состояние и число файлов.
- Строка фильтра (по имени/расширению), переключатель сортировки.
- Сетка превью; видео — значок play и длительность.
- Клик/Enter — полноэкранный просмотр.
- Esc — закрыть попап (из просмотра — вернуться к сетке).

Полноэкранный просмотр (внутри того же `KeyboardPanel`):

- В режиме просмотра `contentWidth/Height` разворачиваются на доступную
  область экрана → карточка почти во весь экран, фон затемнён.
- Изображение `preserveAspectFit`, подпись: имя, дата, размер, номер
  «N из M».
- Видео: постер + кнопка play; воспроизведение — через изолированный
  `VideoView.qml` (`import QtMultimedia`); если модуль/кодек недоступен,
  показывается постер и подпись, ничего не падает.
- Стрелки ←/→ — предыдущий/следующий, Esc — назад к сетке.

Клавиатура: `PanelKeyCatcher`; при активном текстовом фильтре — `blocked`,
чтобы поле получало символы. В просмотрщике `blocked: false`, ловим
`Left/Right/Escape`.

Кнопки: строки-действия в стиле `qs.Ui` (`Button`, `CursorSurface`),
цвета — только из `qs.Commons` (`Color`, `Style`), без хардкода.

## 10. Структура плагина

```
manifest.json                 # id, kinds: [bar-widget], entryPoints.barWidget
Panel.qml                     # бар-пилюля + попап: сетка, фильтр, просмотр
VideoView.qml                 # изолированный плеер QtMultimedia (Loader)
MediaModel.js                 # чистая модель: парсинг, сортировка, фильтр, хэш
bin/oma-mediateka             # status | list | thumb | meta (bash)
install.sh                    # установка в ~/.config/omarchy/plugins/<id>
README.md                     # установка, требования, горячие клавиши
test/MediaModel.test.js       # node-тесты чистой модели
docs/superpowers/specs/…      # эта спека
```

QML импортирует `Connections`-подобный `MediaModel.js` (`import "MediaModel.js" as Model`),
скрипт запускается через `Quickshell.Io.Process` массивами аргументов (без
ручной сборки shell-строки).

## 11. Ошибки и краевые случаи

- Нет бэкенда/телефона/доверия — понятные тексты и команды, не пустой экран.
- `list` вернул пусто при `ready` — «В DCIM нет фото и видео».
- `heif-convert`/`ffmpeg` упали — ячейка остаётся placeholder-иконкой,
  процесс не зацикливается (элемент помечается attempted).
- Отключение во время генерации — `currentThumbKey` сбрасывается, ошибка
  игнорируется, состояние уходит в `no-device`.
- Очень длинные имена — `elide`.
- Несколько iPhone одновременно — берём первый UDID (этап 1).

- `node test/MediaModel.test.js` — парсинг листинга, сортировка, фильтр,

- Экран «телефон не подключён» проверяется всегда; сетка — только когда
  телефон реально смонтирован.

## 14. Этап 2 (реализовано): экспорт

Две операции над выбранным элементом (в полноэкранном просмотре или на
курсоре сетки), по-прежнему **без изменений на телефоне**:

- **«Сохранить»** — `cp` оригинала без перекодирования в `~/Pictures/iPhone`
  (каталог создаётся). Отдельно **«Сохранить как»** — выбор папки через
  `zenity` (или `kdialog`), нативного файлового диалога в `qs.Ui`/`qs.Commons`
  нет. Конфликт имён решается суффиксом ` (1)`, ` (2)`, … (чистая функция
  `MediaModel.uniqueName`, покрыта тестами); копирование никогда не
  перезаписывает. Долгое копирование идёт асинхронным `Process` и показывает
  «Занято…», интерфейс не блокируется.
- **«В буфер обмена»** — фото: `ffmpeg`/`heif-convert` в PNG, затем
  `wl-copy --type image/png`; видео и прочее: путь текстом через `wl-copy`.
  Результат — короткое уведомление в футере/просмотрщике.

Клавиши: `Ctrl+S` — сохранить, `Ctrl+Shift+S` — сохранить как, `Ctrl+C` —
копировать; в поле фильтра не перехватываются. Хелпер получил подкоманды
`names`, `copy`, `clip-image`, `clip-text`, `pick-dir`.
